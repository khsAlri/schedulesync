# schedulesync

직원들의 **프로젝트 참여 일정 공유 · 시간 겹침 확인 · 허가권자 승인**을 위한 웹 시스템입니다.

> **v0.7.0 — 개발 버전**
>
> 핵심 업무, 사이트 내 알림, Slack 연동 및 운영 준비 코드가 포함되어 있습니다.
> 코드 반영은 테스트 통과·배포·운영 승인을 의미하지 않습니다.
> 최신 전체 테스트와 실제 Slack 워크스페이스의 검증 결과는 아직 확인되지 않았습니다.

## 프로젝트 개요

사용자 약 **10명**, 부서 **2개**인 조직을 대상으로 합니다.

| 구분 | 구성 |
| --- | --- |
| 언어 | Python 3.11 이상 |
| 웹 프레임워크 | FastAPI |
| 화면 | Jinja2 기반 서버 렌더링 |
| 데이터 접근 | SQLAlchemy |
| 데이터베이스 | SQLite |
| 외부 연동 | Slack 사용자 조회·DM |
| CI | GitHub Actions |
| 테스트 대상 Python | 3.11, 3.12 |

- 별도 프런트엔드 빌드가 필요하지 않습니다.
- Slack 토큰이 없어도 핵심 업무와 사이트 내 알림을 사용할 수 있습니다.
- 버전 번호는 개발 진행 기록이며, Git 태그 생성이나 운영 배포 완료를 의미하지 않습니다.

## 빠른 시작

### 1. Python 및 가상환경 준비

Python **3.11 또는 3.12**를 준비하고 저장소 루트에서 실행합니다.

| 작업 | 명령어 |
| --- | --- |
| 가상환경 생성 | `python -m venv .venv` |
| 활성화 — Linux/macOS | `source .venv/bin/activate` |
| 활성화 — Windows PowerShell | `.venv\Scripts\Activate.ps1` |
| 의존성 설치 | `python -m pip install -r requirements.txt` |

### 2. 환경 변수 설정

1. `.env.example`을 `.env`로 복사합니다.
2. 다음 명령으로 무작위 서명 키를 생성합니다.

   `python -c "import secrets; print(secrets.token_urlsafe(48))"`

3. 생성한 값을 `.env`의 `SECRET_KEY`에 넣습니다.
4. 로컬 HTTP 개발에서는 `SESSION_HTTPS_ONLY=false`를 사용합니다.
5. Slack 연동이 필요하지 않으면 `SLACK_BOT_TOKEN`을 비워 둡니다.

> **보안 주의**
>
> 실제 `.env`, 비밀번호, 세션 키, Slack 토큰은 저장소나 대화에 넣지 않습니다.

### 3. 관리자 생성 및 서버 실행

| 작업 | 명령어 |
| --- | --- |
| 첫 시스템 관리자 생성 | `python -m app.cli create-admin` |
| 개발 서버 실행 | `uvicorn app.main:app --reload` |

서버 실행 후 [http://localhost:8000](http://localhost:8000)에 접속합니다.

1. 생성한 시스템 관리자로 로그인합니다.
2. 허가권자 2명과 직원 계정을 발급합니다.
3. 초기 비밀번호를 안전한 별도 경로로 전달합니다.

### 다른 PC에서 개발 서버 접속

접속 호스트를 `ALLOWED_HOSTS`에 추가하고 다음 명령으로 실행합니다.

`uvicorn app.main:app --host 0.0.0.0 --reload`

**개발 서버를 그대로 인터넷에 공개하지 않습니다.**

## 환경 변수

| 변수 | 용도 |
| --- | --- |
| `SECRET_KEY` | 필수 세션·미리보기 서명 키. 운영은 무작위 32자 이상 |
| `APP_ENV` | `development` 또는 `production` |
| `DATABASE_URL` | 기본값 `sqlite:///./schedulesync.db`. 현재 업무 변경은 SQLite만 지원 |
| `SLACK_BOT_TOKEN` | Slack Bot Token. 빈 값이면 DM·자동 연결 생략 |
| `APP_BASE_URL` | 경로 없는 기본 주소. DM 링크에 사용 |
| `SESSION_HTTPS_ONLY` | HTTPS에서만 세션 쿠키 전송. 운영은 반드시 `true` |
| `ALLOWED_HOSTS` | 프로토콜·포트 없는 호스트명을 쉼표로 구분 |
| `TZ` | 서버 환경의 시간대. 한국 운영은 `Asia/Seoul` 권장 |

### 운영 환경 설정 원칙

- `APP_ENV=production`으로 설정합니다.
- `APP_BASE_URL`에는 실제 HTTPS 기본 주소를 넣습니다.
- `SESSION_HTTPS_ONLY=true`를 적용합니다.
- `ALLOWED_HOSTS`에는 실제 도메인만 허용합니다.
- 서버 시간대를 운영 기준에 맞춥니다.

운영 모드는 다음 설정을 거부합니다.

- 32자 미만의 서명 키
- HTTP 기본 주소
- 보안 쿠키 해제
- 와일드카드 허용 호스트

운영 모드에서는 API 문서 경로를 비활성화합니다.

## 주요 기능과 업무 규칙

### 로그인 및 계정 관리

- 이메일·비밀번호로 로그인하며 공개 회원가입은 제공하지 않습니다.
- 시스템 관리자는 계정 발급, 정보·역할 수정, 비활성화, 비밀번호 재설정을 수행합니다.
- 비활성화한 계정은 다음 인증 요청부터 기존 로그인도 사용할 수 없습니다.
- 사용자는 본인 비밀번호를 변경할 수 있습니다.
- 비밀번호는 **PBKDF2-SHA256 해시**로 저장합니다.
- 로그인 성공 시 기존 세션을 초기화합니다.
- POST 폼에 CSRF 검사를 적용합니다.
- 관리자는 자기 계정을 비활성화하거나 자기 관리자 역할을 변경할 수 없습니다.
- 프로젝트를 보유한 허가권자 등 기존 데이터와 충돌하는 일부 역할 변경은 차단합니다.

### 프로젝트 등록 및 조회

- 허가권자가 프로젝트와 여러 시간대를 등록합니다.
- **자신이 등록한 프로젝트만 수정·배정**할 수 있습니다.
- 프로젝트 일정과 확정 참여자는 로그인한 직원 전체에게 공개합니다.
- 일정은 한 줄에 다음 형식으로 입력하며 최대 100개입니다.

  `YYYY-MM-DDTHH:MM / YYYY-MM-DDTHH:MM`

- 실제 날짜, 시작·종료 순서, 같은 프로젝트 내부의 일정 중복을 검사합니다.
- 종료 시각과 다음 시작 시각이 같으면 겹침으로 보지 않습니다.

### 배정 및 참여 확정

| 배정 대상 | 확정 방식 |
| --- | --- |
| 일반 직원 | 직원 수락 → 허가권자 전원 승인 |
| 프로젝트 등록자 본인 | 수락·승인 없이 즉시 확정 |
| 다른 허가권자 | 대상 허가권자 수락만으로 확정 |

- 같은 프로젝트·직원의 수락 대기, 승인 대기, 확정 배정은 중복 생성하지 않습니다.
- 일반 직원 배정은 **배정한 허가권자도 승인**해야 합니다.
- 승인 순서는 없으며 한 명이라도 반려하면 전체 반려합니다.
- 승인자는 **직원 수락 시점의 활성 허가권자 전원**으로 고정합니다.
- 지정 승인자의 역할·활성 상태가 바뀌면 승인을 차단합니다. 계정 설정을 복구해야 합니다.

### 직원별 시간 겹침

- 비교 대상은 **같은 직원의 다른 확정 프로젝트 일정**입니다.
- 대기 중인 다른 배정은 비교 대상이 아닙니다.
- 승인할 때마다 최신 겹침을 다시 검사합니다.
- 일반 직원은 시간이 겹쳐도 수락할 수 있지만 승인은 차단합니다.
- 다른 허가권자의 배정은 수락이 곧 확정이므로, 시간이 겹치면 수락 확정을 차단합니다.
- 본인 프로젝트에 본인을 투입하면 다른 확정 프로젝트와 겹쳐도 **경고 후 허용**합니다.

### 확정 후 일정 변경

프로젝트 상세의 **일정 변경** 버튼에서 미리보기 후 제출합니다.

| 조건 | 처리 |
| --- | --- |
| 다른 확정 프로젝트와 겹침 없음 | 즉시 반영 |
| 상대 프로젝트도 본인 등록 | 승인·동의 없이 경고 확인 후 반영 |
| 다른 등록자의 프로젝트와 겹침 | 상대 등록자 승인 + 겹침 당사자 동의 |
| 한 명이라도 거부 | 요청 종료, 기존 일정 유지 |
| 요청자 취소 | 요청 종료, 기존 일정 유지 |

#### 승인·동의 규칙

- 수락·승인 대기 배정이 있으면 먼저 처리해야 합니다.
- 동의 당사자가 허가권자여도 동의를 받습니다.
- 본인 투입 예외를 이후 일정 변경에 자동 확대하지 않습니다.
- 동일인이 등록자이자 당사자이면 승인과 동의를 각각 처리합니다.
- 모든 응답이 완료되기 전까지 기존 일정을 유지합니다.
- 한 프로젝트의 대기 요청 중복을 막습니다.
- 요청 중 새 배정·수락·승인은 차단하되 기존 배정 거절·승인 반려는 가능합니다.

#### 미리보기 및 변경 기준 보호

- 미리보기는 서명하며 **30분 후 만료**됩니다.
- 입력을 수정했다면 다시 미리보기해야 합니다.
- 제출은 서명된 미리보기의 입력을 사용합니다.
- 요청 당시 일정, 관련 확정 배정, 등록자, 계정 역할·활성 상태를 별도 기준 테이블에 저장합니다.
- 제출과 각 승인·동의 시 최신 기준을 비교합니다.
- 마지막 응답과 일정 반영은 하나의 트랜잭션에서 처리합니다.
- 관련 상태가 바뀌면 취소·재요청해야 합니다.
- 겹침이 줄어든 경우에도 보수적으로 재요청합니다.
- 기준 기록이 없는 과거 요청은 반영을 차단하고 취소·재요청하도록 합니다.

## 알림 및 Slack 연동

### 사이트 내 알림

- 업무 변경과 알림 저장은 **같은 트랜잭션**입니다.
- 알림 저장에 실패하면 해당 업무 변경도 롤백합니다.
- 로그인 사용자는 **본인 알림만** 조회·읽음 처리할 수 있습니다.
- 페이지당 20개, 미확인 필터, 개별 읽음, 모두 읽음을 제공합니다.
- 읽음 변경은 CSRF 검사를 적용한 POST로만 처리합니다.
- 목록 조회나 관련 화면 이동만으로 읽음 처리하지 않습니다.
- 메뉴의 미확인 개수는 새로고침·페이지 이동 시 갱신합니다.
- 실시간 푸시는 제공하지 않습니다.
- 읽음 처리는 Slack 상태를 바꾸거나 재발송하지 않습니다.

### Slack 앱 설정

1. 조직 워크스페이스에 Slack 앱과 Bot을 설치합니다.
2. Bot Token 권한을 설정합니다.
3. 권한 변경 후 필요한 경우 워크스페이스에 재설치합니다.
4. 발급된 토큰을 서버의 `SLACK_BOT_TOKEN`으로 주입합니다.
5. 직원 계정의 Slack 사용자 ID를 연결합니다.
6. 테스트 계정에 배정 이벤트를 발생시켜 실제 DM과 링크를 확인합니다.

| Bot scope | 용도 |
| --- | --- |
| `chat:write` | DM 메시지 발송 |
| `im:write` | `conversations.open`으로 DM 대화 열기 |
| `users:read.email` | 로그인 이메일 기반 사용자 조회 |
| `users:read` | 사용자 정보 조회를 위한 기존 설계 권한 |

> 실제 앱 설치, 조직 정책, 사용자 상태는 모의 통신 테스트로 검증할 수 없습니다.
> 운영 워크스페이스에서 별도로 확인해야 합니다.

### 사용자 자동 연결

- 계정 발급 시 ID를 비워 두고 토큰이 있으면 커밋 후 이메일 조회를 예약합니다.
- 수동 ID를 입력했으면 조회하지 않습니다.
- 네트워크 조회 중 DB 세션을 닫습니다.
- 저장 전 다음을 다시 확인합니다.
  - 발급 관리자 권한
  - 대상 계정 활성 상태
  - 이메일 변경 여부
  - 수동 ID 변경 여부
- 다른 계정에 이미 연결된 ID는 자동 연결하지 않습니다.
- 실패해도 계정 발급은 유지합니다.
- 계정 목록을 새로고침해 결과를 확인하고 필요하면 직접 입력합니다.
- 이메일 수정 시 자동 재조회하지 않습니다.
- 기존 계정 소급 조회나 실패 자동 재시도는 없습니다.
- 수동 ID가 올바른 직원의 것인지 관리자가 확인해야 합니다.
- 수동 입력의 계정 간 중복은 현재 차단하지 않습니다.

| 일반 직원 수락 | 수락 시 지정된 허가권자 전원 |
| 배정 거절 | 배정한 허가권자 |
| 전원 승인으로 확정 | 대상 직원과 지정 허가권자 전원 |
| 한 명 반려로 전체 반려 | 대상 직원과 지정 허가권자 전원 |
| 허가권자 간 배정 수락 확정 | 배정한 허가권자 |
| 일정 변경 대기 요청 생성 | 승인·동의 응답자 |
| 일정 변경 즉시 반영 또는 최종 반영 | 요청자, 확정 참여자, 응답자 |
| 일정 변경 거부·취소 | 요청자, 확정 참여자, 응답자 |

- 동일 이벤트 안의 중복 수신자는 제거합니다.
- 비활성·없는 수신자는 건너뜁니다.
- 부분 승인·동의, 화면 겹침 경고, 대기 리마인드는 별도 알림을 생성하지 않습니다.
- 과거 업무 기록에 소급 발송하지 않습니다.

### 발송 순서

1. 업무 변경과 사이트 내 알림을 함께 커밋합니다.
2. HTTP 응답의 백그라운드 작업에서 DM 발송을 시작합니다.
3. 요청과 같은 DB 엔진의 독립 세션으로 발송 데이터를 읽고 선점합니다.
4. DB 세션을 닫은 뒤 Slack에 접속합니다.
5. 발송 결과를 별도 세션으로 저장합니다.

### 발송 상태 및 장애 정책

| 상태 | 의미 |
| --- | --- |
| `pending` | 발송 미시도 |
| `sent` | Slack API 성공 |
| `skipped` | 토큰·사용자 ID 미설정 또는 계정 비활성 등 조건 미충족 |
| `failed` | 실패 또는 발송 결과 불확실 |

- 토큰·사용자 ID가 없거나 계정이 비활성이면 Slack을 건너뛰고 사이트 내 알림은 유지합니다.
- DM 발송 실패는 이미 커밋한 업무·알림을 되돌리지 않습니다.
- 로그에는 내부 식별자와 정규화된 오류 코드만 남깁니다.
- 자동 재시도는 없습니다. 리마인드와 장애 재시도는 다른 개념이지만 현재 둘 다 제공하지 않습니다.
- 선점 후 서버 종료나 결과 저장 실패 시 `failed`와 `delivery_unconfirmed`가 남을 수 있습니다.
- `delivery_unconfirmed`는 실제 DM이 발송되지 않았다는 뜻으로 단정하면 안 됩니다.
- 내구성 있는 작업 큐가 아니므로 커밋 후 작업 시작 전에 서버가 종료되면 DM 또는 자동 연결이 누락될 수 있습니다.
- Slack으로 보낸 알림은 이후 거부·취소되어도 회수하지 않습니다. 현재 업무 상태는 사이트에서 확인해야 합니다.

## 테스트와 CI

### 전체 테스트 실행

1. 개발 의존성을 설치합니다.

   `python -m pip install -r requirements-dev.txt`

2. 전체 테스트를 실행합니다.

   `python -m unittest discover -s tests -v`

### GitHub Actions

Push, pull request, 수동 실행 시 Python **3.11·3.12**에서 다음을 수행합니다.

1. 개발 의존성 설치
2. `pip check`
3. Python 문법 컴파일 검사
4. 전체 `unittest` 실행

CI용 서명 키는 실행 중 무작위로 생성합니다. 운영 토큰이나 운영 DB는 필요하지 않습니다.

### 테스트 구성

아래 파일은 모두 `tests/` 디렉터리에 있습니다.

| 범위 | 파일 |
| --- | --- |
| 배정 순수 규칙·DB 서비스 | `test_assignment_rules.py`, `test_assignment_service.py` |
| 일정 변경 규칙·DB·HTTP | `test_schedule_change_rules.py`, `test_schedule_change_service.py`, `test_schedule_change_http.py` |
| Slack API 모의 통신·자동 연결 | `test_slack_client.py`, `test_slack_mapping.py` |
| 알림 저장·발송·조회·HTTP | `test_notification_service.py`, `test_notification_queries.py`, `test_notification_http.py` |
| 업무 알림 수신자·롤백 | `test_assignment_notifications.py`, `test_schedule_change_notifications.py` |
| 실제 앱 시작·주요 화면·권한·쿠키·운영 설정 | `test_app_smoke.py` |

### 검증 상태

- 테스트는 임시 DB와 모의 Slack을 사용합니다.
- 실제 앱 smoke 테스트도 초기화 함수와 DB 의존성을 임시 DB로 대체합니다.
- 테스트 작성과 실행 통과는 구분합니다.
- 변경안 작성 환경에서는 앱·전체 테스트를 실행하지 않았습니다.
- 실제 CI 로그의 실행 명령, 테스트 수, 마지막 `OK`를 확인해야 합니다.
- CI 성공도 실제 Slack 권한, 브라우저 사용성, 배포 서버의 TLS·파일 권한·복원 가능성까지 보장하지 않습니다.

## 운영 배포 및 백업

### 권장 구성

- 단일 서버·단일 애플리케이션 프로세스
- 영구 로컬 디스크의 SQLite
- 사내망 또는 VPN 접근 권장
- 외부 접속은 TLS 역방향 프록시를 통해 제공
- 서비스 전용 OS 계정으로 애플리케이션 실행
- 개발용 `--reload` 사용 금지
- 프록시에서 인증 경로 요청 제한, 요청 본문 크기 제한, 접근 제어 설정

운영 실행 예시:

`uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1`

프록시는 실제 접속 호스트를 전달하고 웹 서비스의 HTTPS 연결을 종료해야 합니다.

- 프록시 신뢰 설정은 실제 프록시 주소에 한정합니다.
- 모든 발신자의 전달 헤더를 신뢰하지 않습니다.
- 장시간 동작은 systemd 등 운영 환경의 프로세스 관리자로 실행합니다.
- 이 저장소는 특정 호스팅 업체에 자동 배포하지 않습니다.

### 초기화 및 업그레이드

- 관리자 CLI 또는 앱 시작 시 없는 테이블을 생성합니다.
- `schedule_change_baselines`는 5단계에서 추가된 요청 기준 테이블입니다.
- **기존 DB를 삭제하지 않습니다.**
- `create_all`은 기존 테이블 컬럼 변경이나 데이터 마이그레이션을 하지 않습니다.
- 스키마 변경이 생기면 별도 마이그레이션을 준비합니다.

### 백업·복원

1. 백업 시각, 앱 버전, DB 절대 경로를 기록합니다.
2. 단순 파일 복사 방식이면 앱을 중지하고 DB 연결이 모두 종료되었는지 확인합니다.
3. SQLite DB를 접근 제한된 별도 저장소에 복사합니다.
   - 운영 중 백업은 SQLite의 일관된 백업 API 또는 전용 도구를 사용합니다.
4. `.env`와 비밀 값은 DB와 별도로 암호화해 보관합니다. 저장소에 넣지 않습니다.
5. 복원은 앱 중지 후 수행하고 파일 소유자·권한을 복구합니다.
6. 별도 환경에서 로그인·프로젝트·승인·알림 데이터와 DB 무결성을 확인한 뒤 서비스를 재개합니다.
7. 정기적으로 실제 복원 연습을 합니다.

> 서명 키를 교체하면 기존 세션과 일정 변경 미리보기 토큰이 무효화됩니다.
> 키 유출 시 교체하고 Slack 토큰도 필요에 따라 폐기·재발급합니다.

## 알려진 제한

### 데이터베이스 및 성능

- SQLite는 조회도 `BEGIN IMMEDIATE` 잠금을 사용합니다. 부하가 늘면 요청이 대기·실패할 수 있습니다.
- PostgreSQL 이전은 URL 변경만으로 끝나지 않습니다. 드라이버·잠금 전략·마이그레이션 검증이 필요합니다.
- 프로젝트·배정·변경 요청 목록은 전체 로드 방식입니다. 알림 목록만 페이지 이동을 지원합니다.
- 시각은 서버 현지 시각의 `naive datetime`입니다. 사용자별 시간대 변환은 없습니다.

### 인증 및 계정 운영

- 로그인 실패 제한은 앱에 없습니다. 프록시 제한과 사내망·VPN을 적용해야 합니다.
- 비밀번호 변경·관리자 재설정으로 다른 브라우저의 기존 세션을 즉시 무효화하지 않습니다.
- 강제 전체 로그아웃이 필요하면 계정 비활성화 또는 서명 키 교체를 운영상 검토해야 합니다.
- 역할이 바뀐 진행 중 승인 요청은 막힐 수 있습니다. 조직 변경 전에 대기 요청을 정리해야 합니다.

### 제공하지 않는 기능

- 배정 취소 화면: 취소 상태는 DB 모델에만 있습니다.
- 프로젝트 종료·삭제
- 개인 일정·휴가 관리
- 셀프 신청
- 승인 리마인드
- Slack 발송 보장·자동 재시도·수동 재발송 UI·상세 운영 대시보드
- 모바일 전용 앱·실시간 푸시

### 기타

- 일부 기존 주석과 오류 문구에는 이전 단계 안내나 일본어가 남아 있습니다.
- 의존성 버전은 범위 지정이며 완전 고정 lock 파일은 없습니다. 배포 시 검증한 환경을 기록해야 합니다.
- 작은 화면에서의 최종 사용성은 별도로 확인해야 합니다.

## 시스템 요구사항

| 항목 | 내용 |
| --- | --- |
| 목적 | 직원들의 프로젝트 참여 일정 공유, 프로젝트 간 시간 겹침 확인, 허가권자 승인을 통한 참여 확정 |
| 규모 | 사용자 약 10명, 부서 2개 |
| 허가권자 | 부서장 2명(이하 A, B). 조직 규칙으로 지정 |
| 프로젝트 등록 | 허가권자만 등록. **자신이 등록한 프로젝트만** 수정·배정 |
| 참여 방식 | 허가권자가 직원을 배정 → 직원이 수락 또는 거절. 셀프 신청 없음 |
| 일반 직원 배정 승인 | 직원 수락 뒤 **허가권자 전원(배정한 허가권자 포함)이 각각 승인**. 순서 없음. 1명이라도 반려하면 전체 반려 |
| 허가권자 본인 투입 | 자기 프로젝트에 자신을 투입할 때 **누구의 승인도 필요 없음**. 다른 확정 프로젝트와 겹쳐도 **경고만 하고 허용** |
