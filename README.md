# schedulesync
스케줄관리 시스템

v1 시스템 개발 시작

## 현재 버전

**v0.5.0 — 확정 후 일정 변경 요청·승인·동의까지 구현한 개발 버전**

v1 완성을 목표로 단계별 개발을 진행한다. 현재 1~5단계 코드가 반영되어 있다. 사이트 내 알림, 슬랙 DM 발송 및 이메일 기반 슬랙 사용자 자동 조회는 아직 구현되지 않았다.

버전 번호는 개발 진행 기록용이다. Git 태그 생성이나 운영 배포 완료를 의미하지 않는다. 이전 버전 기록은 단계별 변경 내용을 정리한 것이며, 각 버전의 태그가 존재한다는 의미는 아니다.

코드 반영과 검증 완료는 구분한다. 자동 테스트 파일은 추가되어 있으나, 이 문서 작성 시점에 최신 테스트 실행 로그와 전체 통과 여부는 확인되지 않았다.

## 개발 진행 현황

| 단계 | 구현 범위 | 상태 |
|---|---|---|
| 1단계 | 프로젝트 기본 구조, 환경 변수 설정, DB 모델, 기본 화면 | 코드 반영 |
| 2단계 | 로그인·로그아웃, 첫 관리자 생성, 계정 관리, 비밀번호 변경 | 코드 반영 |
| 3단계 | 프로젝트 등록·수정, 여러 일정 입력, 프로젝트 및 확정 참여 현황 조회 | 코드 반영 |
| 4단계 | 직원 배정·수락·거절, 전원 승인·반려, 프로젝트 간 직원별 시간 겹침 검사 | 코드 반영·테스트 결과 미확인 |
| 5단계 | 확정 후 일정 변경 미리보기·요청·승인·동의·거부·취소 | 코드 반영·테스트 결과 미확인 |
| 6단계 | 사이트 내 알림, 슬랙 DM, 이메일 기반 슬랙 사용자 자동 조회 | 미구현 |
| 7단계 | 테스트 보강, 운영 설정 점검, 실행·배포 문서 정리 | 미진행 |

### 현재 배정·승인 동작

- 허가권자는 자신이 등록한 프로젝트에 활성 직원 또는 활성 허가권자를 배정할 수 있다.
- 같은 프로젝트의 같은 사용자에게 수락 대기·승인 대기·참여 확정 배정이 있으면 중복 배정을 막는다.
- 일반 직원은 본인에게 온 배정을 수락하거나 거절한다.
- 일반 직원이 수락하면 수락 시점의 활성 허가권자 전원을 승인자로 저장한다. 배정한 허가권자도 포함한다.
- 승인 순서는 없으며 전원이 승인하면 참여가 확정된다. 한 명이라도 반려하면 전체 반려된다.
- 이미 응답했거나 종료된 상태의 요청에 대한 중복 응답을 차단한다.
- 허가권자가 자기 프로젝트에 자신을 투입하면 수락·승인 없이 즉시 확정한다. 다른 확정 프로젝트와 겹치면 경고를 표시하지만 허용한다.
- 다른 허가권자의 프로젝트에 배정된 허가권자는 본인의 수락만으로 확정된다. 이 경우 다른 확정 프로젝트와 시간이 겹치면 수락 처리를 차단한다.
- 일반 직원은 시간이 겹쳐도 수락할 수 있지만 승인은 차단한다.
- 시간 겹침은 같은 사용자의 다른 확정 프로젝트 일정과 비교한다. 대기 중인 배정이나 다른 사용자의 일정은 비교 대상이 아니다.
- 승인은 매번 최신 확정 프로젝트 일정을 다시 검사한다. 먼저 일부 승인했더라도 마지막 승인 시점에 겹침이 생겼으면 확정을 차단한다.
- 종료 시각과 다른 일정의 시작 시각이 같으면 겹침으로 보지 않는다.
- 배정·승인 화면에는 내가 받은 배정, 내 프로젝트의 배정, 내가 승인자로 지정된 배정을 표시한다.
- 확정 참여 현황은 프로젝트 화면에서 로그인한 전 직원이 조회할 수 있다.

### 현재 일정 변경 동작

- 허가권자는 자신이 등록한 프로젝트 상세 화면의 **일정 변경** 버튼에서 변경을 시작한다.
- 일정 입력 형식은 한 줄당 `YYYY-MM-DDTHH:MM / YYYY-MM-DDTHH:MM`이며 최대 100개까지 입력한다.
- 기존 일정과 같은 변경은 요청하지 않는다.
- 미리보기에서 변경 후 일정, 겹침 영향을 받는 참여자, 상대 프로젝트, 필요한 승인·동의 목록을 표시한다.
- 비교 대상은 변경 프로젝트의 확정 참여자들이 참여하는 다른 확정 프로젝트다. 변경 후에도 유지되는 기존 겹침 역시 검사 대상이다.
- 겹침이 없으면 별도 승인·동의 없이 제출 시 즉시 반영한다.
- 상대 프로젝트도 요청자 본인 등록이면 승인·동의를 생략한다. 다만 겹침 경고 확인은 필수다.
- 다른 등록자의 프로젝트와 겹치면 그 등록자의 승인과 겹침 영향을 받는 참여자의 동의가 필요하다.
- 본인 등록 프로젝트와 다른 등록자의 프로젝트가 함께 겹치면, 다른 등록자 프로젝트에 필요한 승인·동의는 유지한다.
- 겹침 당사자가 허가권자여도 참여자 동의를 받는다. 본인 투입 시의 무승인 예외를 이후 일정 변경에 자동 적용하지 않는다.
- 같은 사람이 상대 등록자이면서 참여자이면 승인과 동의를 각각 처리한다.
- 모든 승인·동의가 완료되기 전까지 원래 프로젝트 일정을 유지한다.
- 한 명이라도 거부하면 요청은 거부 상태로 종료되고 원래 일정을 유지한다.
- 요청자는 본인이 생성한 대기 요청을 취소할 수 있다. 종료된 요청에는 다시 응답하거나 취소할 수 없다.
- 같은 프로젝트에는 대기 중인 일정 변경 요청을 중복 생성할 수 없다.
- 수락·승인 대기 배정이 있는 프로젝트는 해당 배정을 먼저 처리해야 일정 변경을 요청할 수 있다.
- 대기 중인 일정 변경 요청이 있는 프로젝트는 새 배정·배정 수락·승인을 차단한다. 기존 배정 거절과 승인 반려는 가능하다.
- 미리보기는 사용자·프로젝트·입력 일정·비교 기준을 포함해 서명하며 30분 후 만료된다.
- 제출할 때는 미리보기의 입력을 사용한다. 화면 위의 일정 입력을 수정했다면 미리보기를 다시 실행해야 한다.
- 미리보기 후 관련 상태가 바뀌면 제출을 차단한다.
- 승인·동의할 때마다 요청 당시 기준과 최신 상태를 비교한다. 마지막 응답과 일정 반영도 같은 트랜잭션에서 처리한다.
- 요청 기준에는 변경 전·후 일정, 관련 확정 배정, 상대 프로젝트 일정·등록자, 관련 계정의 역할·활성 상태를 저장한다.
- 관련 상태가 달라지면 기존 요청의 반영을 차단한다. 요청자는 취소 후 최신 내용을 확인해 다시 요청해야 한다.
- 겹침이 줄어들거나 겹치지 않는 관련 확정 프로젝트가 바뀐 경우에도 보수적으로 재요청을 요구한다.
- 요청 목록에는 내가 생성한 요청, 내 프로젝트의 요청, 내가 응답자로 지정된 요청을 표시한다.
- 요청 목록에서 요청 당시 기존 일정·겹침·상대 프로젝트 일정, 변경 일정과 응답 내역을 확인할 수 있다.
- 기준 기록이 없는 요청은 승인 반영을 차단하고 취소·재요청하도록 한다.

### 현재 제한 사항

- 배정·수락·승인 및 일정 변경 상태 변경은 현재 SQLite에서만 지원한다. 다른 DB는 동시성 보호 구현 전까지 서비스 계층에서 차단한다.
- SQLite는 `BEGIN IMMEDIATE`로 트랜잭션 시작부터 예약 잠금을 확보한다. 조회도 같은 잠금 방식을 사용하므로 동시 요청은 대기하거나 제한 시간 초과로 실패할 수 있다. 사용자 약 10명 규모를 전제로 한 구현이다.
- PostgreSQL 등으로 전환하려면 접속 주소 변경뿐 아니라 별도 드라이버와 잠금 전략을 구현·검증해야 한다.
- 배정 승인자 목록은 직원 수락 시점에 고정한다. 이후 추가된 허가권자를 진행 중 요청에 자동 추가하지 않는다.
- 저장된 배정 승인자의 역할이나 활성 상태가 바뀌면 승인을 차단한다. 승인자를 자동 제외하지 않으며, 관리자가 계정 설정을 확인·복구해야 한다.
- 진행 중인 배정(수락 대기·승인 대기·참여 확정) 또는 대기 중인 일정 변경 요청이 있는 프로젝트는 일반 프로젝트 수정 화면에서 일정을 직접 수정할 수 없다. 이름과 설명은 수정할 수 있다.
- 확정 참여자가 있는 프로젝트의 일정은 별도 일정 변경 화면에서 처리한다. 수락·승인 대기 배정은 먼저 처리해야 한다.
- 배정 취소 화면은 아직 없다. 취소 상태는 DB 모델에만 정의되어 있다.
- 시각은 시간대 정보 없는 서버 현지 시각으로 저장한다. 사용자별 시간대 변환 기능은 없다.
- 슬랙 사용자 ID는 현재 관리자가 직접 입력한다. 이메일 자동 조회와 실제 DM 발송은 6단계에서 구현한다.
- 알림 관련 DB 모델은 있으나 사이트 내 알림 화면과 발송 처리는 아직 없다.
- 로그인 실패 횟수 제한은 아직 없다.
- 활성 허가권자가 2명을 초과하면 경고하지만 계정 생성을 차단하지는 않는다.
- 일부 기존 화면 문구와 주석에는 이전 단계의 안내 또는 일본어가 남아 있다. 기능 상태는 이 문서의 개발 진행 현황을 기준으로 확인한다.
- 운영 배포 전 HTTPS, 세션 쿠키 보안 설정, DB 마이그레이션·백업 등을 별도로 점검해야 한다.

## 테스트 및 검증 상태

개발용 의존성을 `pip install -r requirements-dev.txt`로 설치한 뒤 `python -m unittest discover -s tests -v`로 실행한다.

`requirements-dev.txt`는 운영용 의존성과 HTTP 테스트용 `httpx`를 함께 설치한다. CI에서도 개발용 의존성을 설치해야 HTTP 테스트를 실행할 수 있다.

| 파일 | 검사 범위 |
|---|---|
| `tests/test_assignment_rules.py` | 직원별 겹침 판단, 경계 시각, 본인 투입, 허가권자 간 배정, 전원 승인·반려, 중복 응답 |
| `tests/test_assignment_service.py` | 임시 SQLite DB를 사용한 배정·승인 흐름, 권한·활성 상태, 중복 처리, 최종 승인 재검사, 연속 일정, DB 잠금 차단 및 해제 후 재시도 |
| `tests/test_schedule_change_rules.py` | 일정 변경 겹침 계획, 본인 등록 프로젝트 예외, 필요한 승인·동의, 전원 응답, 거부, 중복 응답 |
| `tests/test_schedule_change_service.py` | 임시 SQLite DB를 사용한 요청·즉시 반영·승인·동의·거부·취소, 비교 기준 변경 차단, 권한 및 요청 중복 방지 |
| `tests/test_schedule_change_http.py` | 실제 로그인·세션·CSRF와 일정 변경 라우터·템플릿을 연결한 미리보기·제출·응답·취소, 권한 차단, 위조·만료 처리, 정적 파일 경로 |

- 순수 업무 규칙 테스트는 DB와 웹 서버 없이 실행할 수 있다.
- DB 서비스 테스트는 별도 임시 SQLite DB를 사용하며 운영 DB를 사용하지 않는다.
- HTTP 테스트는 별도 테스트 앱과 임시 DB를 사용하며 운영 앱의 lifespan을 실행하지 않는다.
- 테스트 앱에 정적 파일 경로를 등록하고 로그인 화면과 CSS 응답을 검사하도록 수정했다.
- 테스트 코드 추가 및 수정은 반영되었으나 최신 실행 로그와 통과 여부는 확인되지 않았다.
- CI 화면의 성공 표시는 해당 검사 범위의 성공을 뜻한다. 전체 테스트 통과 여부는 실제 실행 명령과 로그를 확인해야 한다.
- 운영 앱 전체의 미들웨어·오류 처리·시작 과정에 대한 통합 검증과 실제 브라우저·운영 환경 검증은 별도로 필요하다.
- DB 잠금 테스트는 기본 잠금 동작을 검사한다. 모든 동시 요청 조합에 대한 검증 완료를 의미하지 않는다.

## DB 변경 안내

- 5단계에서 요청 당시 비교 기준을 보관하는 `schedule_change_baselines` 테이블을 추가했다.
- 서버 재시작 시 초기화 과정에서 없는 테이블을 생성한다.
- 이 변경을 위해 기존 DB를 삭제할 필요는 없다.
- 현재 초기화는 없는 테이블 생성만 수행하며 기존 테이블의 컬럼 변경이나 데이터 마이그레이션을 자동 수행하지 않는다.
- 기준 기록이 없는 과거 일정 변경 요청은 승인 반영이 차단된다. 취소 후 다시 요청해야 한다.
- 운영 DB를 변경하거나 업그레이드하기 전에는 별도 백업이 필요하다.

## 버전별 변경 이력

## 시스템 요구사항

아래 표는 최종 목표 요구사항이다. 현재 구현 여부는 위의 개발 진행 현황을 기준으로 확인한다.

| 항목 | 내용 |
|---|---|
| 목적 | 직원들의 프로젝트 참여 일정 공유, 프로젝트 간 시간 겹침 확인, 허가권자 승인을 통한 참여 확정 |
| 규모 | 사용자 약 10명, 부서 2개 |
| 허가권자 | 부서장 2명(이하 A, B). 조직 규칙으로 지정 |
| 프로젝트 등록 | 허가권자만 등록. **자신이 등록한 프로젝트만** 수정·배정 |
| 참여 방식 | 허가권자가 직원을 배정 → 직원이 수락 또는 거절. 셀프 신청 없음 |
| 일반 직원 배정 승인 | 직원 수락 뒤 **허가권자 전원(배정한 허가권자 포함)이 각각 승인**. 순서 없음. 1명이라도 반려하면 전체 반려 |
| 허가권자 본인 투입 | 자기 프로젝트에 자신을 투입할 때 **누구의 승인도 필요 없음**. 다른 확정 프로젝트와 겹쳐도 **경고만 하고 허용** |
| 허가권자 간 배정 | A가 B를 A의 프로젝트에 배정하면 **B 수락**만으로 확정. 승인 없음 |
| 시간 겹침 | 비교 대상은 프로젝트 일정끼리만. 실제 시간이 겹치지 않으면 여러 프로젝트 동시 참여 가능. 겹치면 **경고와 함께 승인 차단** |
| 확정 후 일정 변경 | 다른 확정 프로젝트와 겹치게 되면 경고. 상대 프로젝트를 등록한 허가권자 승인 + 참여 직원 동의가 있어야 반영. 상대 프로젝트도 본인 등록이면 경고 확인 후 저장(직원 동의 불필요) |
| 개인 일정 | 관리하지 않음. 휴가 등 개인 사정은 직원이 배정을 거절해 처리 |
| 공개 범위 | 누가 어떤 프로젝트에 참여 중인지 전 직원에게 공개 |
| 로그인 | 시스템 관리자가 계정 발급, 이메일·비밀번호 로그인 |
| 외부 연동 | 없음(구글 로그인·캘린더 연동 삭제). 슬랙 DM 알림 발송만 사용 |
| 알림 | 인앱 알림 + 슬랙 DM |
| 승인 대기 리마인드 | 없음 |
| 시스템 관리자 | 별도 역할 |
| 개발 형태 | 직접 개발 |
| 운영 형태 | 웹페이지. 직원이 웹 브라우저로 접속해 사용 |

## 슬랙 DM 알림 설계

아래 내용은 6단계 구현을 위한 설계이다. 현재 실제 슬랙 연동과 알림 발송은 구현되지 않았다.

### 1. 토큰 관리

- 슬랙 앱(Bot)을 워크스페이스에 설치하고 발급된 **Bot Token**을 사용한다.
- 토큰은 코드·저장소에 넣지 않고 환경 변수 `SLACK_BOT_TOKEN`으로만 주입한다.
- 필요한 Bot Token 권한(scope)

| scope | 용도 |
|---|---|
| `chat:write` | 직원에게 DM 발송 |
| `users:read` | 슬랙 사용자 정보 조회 |
| `users:read.email` | 이메일로 슬랙 사용자 ID 조회 |

### 2. 직원 계정 ↔ 슬랙 사용자 매핑

- 사용자(직원) 정보에 `slack_user_id` 항목을 둔다. (예: `U01ABCDEF`)
- 시스템 관리자가 계정을 발급할 때 로그인 이메일로 슬랙 사용자 ID를 자동 조회해 저장한다.
- 슬랙 이메일이 로그인 이메일과 달라 조회에 실패하면 시스템 관리자가 직접 입력한다.
- `slack_user_id`가 비어 있는 사용자는 슬랙 DM을 건너뛰고 인앱 알림만 받는다.

### 3. 알림 발송 시점

| 이벤트 | 받는 사람 |
|---|---|
| 프로젝트에 배정됨 | 배정된 직원(허가권자 포함) |
| 직원이 배정을 수락함 (승인 필요) | 허가권자 전원 |
| 직원이 배정을 거절함 | 배정한 허가권자 |
| 허가권자 전원 승인 → 참여 확정 | 해당 직원, 허가권자 전원 |
| 허가권자 1명 반려 → 전체 반려 | 해당 직원, 허가권자 전원 |
| 허가권자 간 배정 수락 → 참여 확정 | 배정한 허가권자 |
| 확정 후 일정 변경으로 겹침 발생 → 승인·동의 요청 | 상대 프로젝트를 등록한 허가권자, 참여 직원 |
| 일정 변경 승인·동의 완료 또는 거부 | 일정을 변경한 허가권자, 참여 직원 |

- 시간 겹침 **경고**는 화면에서 바로 보여 주며 따로 알림을 보내지 않는다.
- 승인 대기 리마인드는 보내지 않는다(요구사항 기준).

### 4. 발송 실패 처리

- 인앱 알림을 먼저 저장하고 슬랙 DM은 그다음에 발송한다. 슬랙 발송이 실패해도 인앱 알림과 업무 처리(배정·승인 등)는 그대로 유지한다.
- 실패한 건은 오류 내용과 함께 로그로 남긴다. 리마인드가 없다는 원칙에 따라 자동으로 다시 보내지 않는다.
